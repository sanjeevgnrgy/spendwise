# Phase 10: Agent uses MCP

> **Later changes:** after Phase 18, the default `MCP_URL` became `http://127.0.0.1:8000/mcp/`. The trailing slash
> avoids a redirect, and 127.0.0.1 avoids trying IPv6 first ([decisions.md](../decisions.md) D136). Examples below
> still show the old form; both work.

**Goal:** the assistant's agent stops using its own local tool functions. It becomes an **MCP client**: it asks
the MCP server which tools exist, shows them to Gemini, and sends every tool call to the MCP server.
`modules/assistant/tools.py` is deleted.

> **Not run yet.** At the developer's request, this phase was written without starting the server or calling
> Gemini. The code compiles, and the MCP client calls it uses (`list_tools`, `call_tool`, `read_resource`,
> `is_error`, the `/mcp` URL) were checked against the running server before the code was written. The full
> `/chat` flow through MCP has not been exercised. See "Test it by hand".

## Concepts

**Before (Phases 7–9):** the agent had its own Python functions (`assistant/tools.py`) that called the expenses
module. The list of tools, and how to describe them to Gemini, lived in the assistant's code.

**Now:** the agent knows only a URL, `MCP_URL`. At runtime it:
1. **Discovers** the tools: `list_tools()` returns each tool's name, description and input schema.
2. **Translates** each one into a Gemini function declaration (same information, Gemini's format).
3. **Delegates** every call: when Gemini asks for `add_expense(...)`, the agent sends `call_tool("add_expense", ...)`
   to the MCP server and passes the result back.

**Analogy:** before, the assistant kept its own toolbox, copied from the workshop's. Now it has the workshop's
phone number. It calls to ask "what can you do?", and then asks the workshop to do each job. If the workshop
adds a tool or moves to another building, the assistant only needs the new number.

**What we gained:**
- **The agent no longer depends on the expenses module.** `agent.py` imports no business module and takes no
  database session. Everything it knows about expenses arrives over MCP, including the category list (from the
  `expenses://categories` resource).
- **One copy of the tools.** The near-duplicate from Phase 9 is gone. A tool added to the MCP server becomes
  available to the assistant (after a restart) without touching assistant code.
- **The MCP module can move.** Today `MCP_URL` points at this same app. If the MCP module became its own service,
  on another port or machine, only `MCP_URL` in `.env` would change.

**What it costs:** each tool call is now an HTTP round trip instead of a function call (slower, and it can fail),
and the app talks to itself over the network. That's the usual trade for a looser coupling.

**Honest footnote:** the *assistant module* still imports two public interfaces for `POST /parse` (Phase 6):
`categories` (the list to choose from) and `expenses.PaymentMethod` (the allowed values). The claim "no direct
dependency on expenses" is true for the agent and `/chat`, not yet for `/parse`.

## What was built

| File | What |
|---|---|
| `modules/assistant/mcp_client.py` | **New.** Connects to `MCP_URL` over Streamable HTTP; `tool_declarations()`, `call_tool()`, `category_names()` |
| `modules/assistant/agent.py` | The loop now runs tools through `mcp_client`; no session, no local tools |
| `modules/assistant/tools.py` | **Deleted** |
| `modules/assistant/service.py` | Calls `agent.run(message, today, history)` (no session) |
| `core/config.py`, `.env.example` | `MCP_URL`, default `http://localhost:8000/mcp` |

**Schema conversion** (`mcp_client.py`). An MCP tool's input schema is JSON Schema, generated by Pydantic. Gemini
wants a simpler shape, so:
- optional arguments, which arrive as `anyOf: [X, null]`, become just `X` (and stay out of `required`),
- only `type`, `description`, `enum`, `items` and `format` are kept; `title` and `default` are dropped.

```python
def _to_declaration(tool):
    schema = tool.input_schema or {}
    return {
        "type": "function",
        "name": tool.name,
        "description": tool.description or "",
        "parameters": {"type": "object",
                       "properties": {name: _simplify(prop) for name, prop in schema.get("properties", {}).items()},
                       "required": schema.get("required", [])},
    }
```

**The loop's tool step** (`agent.py`):

```python
result = _run_tool(call.name, arguments)          # mcp_client.call_tool(...) + logging
turn.append({"type": "function_result", "name": call.name, "call_id": call.id,
             "is_error": not result.ok, "result": [{"type": "text", "text": result.text}]})
```

**Error handling:**

| Situation | What happens |
|---|---|
| The tool reports a problem (MCP `isError`, e.g. "Unknown category 'Snacks'") | Passed to Gemini as an error result; it corrects its call or explains. `tool_calls[].ok` is `false` |
| MCP server unreachable **before** the loop (can't list tools) | Gemini isn't called. Reply: "Sorry, I can't reach the expense tools right now..." (HTTP 200, stored in the thread) |
| MCP server unreachable **during** a tool call | Gemini is told "The expense tools are unreachable right now" as an error result, and tells the user |
| MCP server doesn't answer within 15 s | Treated as unreachable |

Design notes:
- **Tools are listed on the first chat, not at app startup,** then cached. By default the MCP server is this same
  app, which isn't answering requests yet while it starts. Restart the app to pick up new tools.
- **One short connection per operation.** The MCP SDK is async and the agent runs in a worker thread, so each
  operation runs in its own small event loop (`asyncio.run`). Simple, and fine for a stateless local server.
- **`/chat` must stay a plain `def` route.** It calls this same app's `/mcp`; an `async def` route that blocked
  the event loop while waiting for its own server would deadlock.

## Run it

From the project folder: `.\run.ps1`. No new packages.

**If you run on another port** (e.g. `.\run.ps1 --port 8001`), set `MCP_URL=http://localhost:8001/mcp` in `.env`,
or the assistant will look for its tools on port 8000.

## Test it by hand

These are the checks to run; none has been run yet.

1. **Normal chat.** In `/docs`, `POST /chat` `{"message": "How much did I spend on food this month?"}`.
   Expect a reply with a total, and in the terminal lines like
   `tool call (MCP): get_summary({"month": "2026-11"})` followed by the result. You should also see uvicorn log
   `POST /mcp/` requests: that's the app calling itself.
2. **A tool error.** `{"message": "Add 50 rupees for chips at a shop today, cash, category Snacks"}`.
   Expect the terminal to show `-> ERROR Error executing tool add_expense: Unknown category 'Snacks'...`, and the
   reply to ask which real category to use (or to pick one and say so).
3. **Unreachable server.** Stop the app, set `MCP_URL=http://localhost:9999/mcp` in `.env`, start it, and send any
   `/chat` message. Expect **200** with "Sorry, I can't reach the expense tools right now...", an empty
   `tool_calls`, and no Gemini step in the terminal. Remove the line from `.env` afterwards and restart.
4. **Memory still works.** Send a follow-up with the `thread_id` from step 1.

If step 1 fails with Gemini rejecting the request (a 502 mentioning the tools or schema), the converted
declarations are the first place to look: `mcp_client._simplify`.

## Check your understanding

**1. How does the agent know that a tool called `get_summary` exists and takes a `month` argument?**

<details><summary>Answer</summary>

It asks the MCP server. `mcp_client.tool_declarations()` calls `list_tools()`, which returns each tool's name,
description and input schema. Those are converted into Gemini function declarations and sent with every request.
Nothing about `get_summary` is written in the assistant's code any more.
</details>

**2. The MCP module is moved to its own service on another machine. What has to change in the assistant?**

<details><summary>Answer</summary>

Only the `MCP_URL` setting in `.env`. The agent discovers tools and runs them through that URL, so its code is
unchanged. (The new service would need its own access to the database, and should be protected with
authentication once it's reachable over a network.)
</details>

**3. What is the difference between a tool result with `isError` and the MCP server being unreachable, and how
does the agent treat each?**

<details><summary>Answer</summary>

`isError` means the server was reached and the tool ran, but reported a problem, such as an unknown category.
That's useful information, so it goes back to Gemini as an error result, and Gemini can fix its call or explain.
Unreachable means no answer at all. If that happens before the loop, the agent can't even list tools, so it
replies with an apology without calling Gemini. If it happens during a call, Gemini is told the tools are
unreachable and passes that on to the user.
</details>
